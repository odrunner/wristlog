## Why S1 and S2 were missed before

Both are **emergent** bugs: every individual policy is defensible, and reviewing them
one at a time finds nothing. The bug only exists because Postgres ORs permissive
policies together, so a careless policy silently overrides a careful one sitting right
next to it. `watches` has a correct privacy policy — it is simply unreachable.

This is worth a standing rule: **never add a second permissive `SELECT` policy to a
table that already has a privacy-aware one.** Tighten the existing policy instead.

The codebase already demonstrates the correct pattern elsewhere — all 21 demo-account
read-only guards are `RESTRICTIVE`, so they intersect rather than OR. The privacy
policies just didn't get the same treatment.

## Recommended order

**0. R7 first — `npx supabase db dump --linked -f sql/schema.sql`.** One read-only
command, and it captures the pre-change schema in the repo before anything is edited.

**1. Privacy (S1, S2)** — pure SQL, deployable via `supabase db query --linked`.
Rollback is pre-captured at `sql/2026-08-13-privacy-rls-rollback.sql` (generated from
`pg_policies` before any change; DDL touches access rules only, never row data).

Do **not** branch-test this — see R7: a Supabase branch builds from
`supabase/migrations/`, which diverged in May and does not contain these policies.
Validate instead by:

1. **Read-only simulation** — run each affected surface (feed author names, search,
   followers modal, mention autocomplete) under the *candidate* predicate as a test
   user and diff row counts against today's result. Real schema, real data, no DDL.
2. **Transactional apply** — `BEGIN` → drop/create → verify → `COMMIT` or `ROLLBACK`.
   DDL is transactional in Postgres, so a bad result never lands.
3. **UAT on both test accounts** before considering it done.

**2. Database performance (P1, P3)** — under 30 minutes combined:

```sql
ANALYZE;
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_follows_following ON follows(following_id);
-- + logs(watch_id), wishlist(user_id), notifications(actor_id), user_blocks(blocked_id)
```

Real load off an instance with **406 MB of RAM and almost no headroom**. Use
`CONCURRENTLY` — a plain `CREATE INDEX` locks the table.

**3. P2** — script the `(SELECT auth.uid())` rewrite across 215 policies. Zero
behaviour change, so it's safe at that scale. Do it *after* step 1 so you don't
rewrite policies you're about to drop.

**4. R1 + R2** — the `safeLS` wrapper and the toast fix. Mechanical, high user value.

**5. S3, U1, U2** — XSS sink removal, avatar `alt` text, central Escape/focus handling.
