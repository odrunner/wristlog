# WRotate Correctness-Bug Audit

**Date:** 2026-06-22
**Scope:** Recently-changed admin/follow/campaign logic, edge functions (Deno/TS), timegrapher/measurement math, analytics scripts, and the client feed/notification paths.
**Method:** Each finding was traced end-to-end through the actual code path before inclusion. File:line citations refer to the working tree at commit e695a44.

---

## High

### H1. `acceptFollowRequest` bails on a duplicate `follows` row, leaving a stuck request
- **File:** `index.html:8610-8630`
- **What's wrong:** `acceptFollowRequest` does a raw `db.from('follows').insert({...})` (line 8613). If a `follows` row already exists for `(requester, accepter)` — which is now *reachable* because `sendFollowRequest`'s self-heal (commit fa051aa, line 8568-8577) and other paths can create a `follows` row while a `follow_request` is still pending — the insert returns a `23505` unique violation. `followErr` is truthy, so the function immediately `return`s at line 8614 **before** deleting the stale `follow_request` (line 8616) and **before** marking the notification read (line 8624).
- **Why it's a bug:** The requester already follows the accepter, but the pending `follow_request` row is never cleared and the accepter's notification keeps showing Accept/Decline buttons indefinitely. Tapping Accept appears to do nothing (toast "Could not accept request"). This is exactly the contradictory `follows` + `follow_requests` state that commits fa051aa/f78fff6 were trying to eliminate — the accept path was not given the same self-healing treatment as `sendFollowRequest`/`followUser`.
- **Suggested fix:** Treat `23505` as success (like `followUser` does at line 8551): on `followErr?.code === '23505'`, fall through to delete the request, mark the notification read, and re-render. Only abort on other errors.
- **Severity:** High · **Confidence:** High

### H2. `resend-webhook` never verifies the webhook signature
- **File:** `supabase/functions/resend-webhook/index.ts:5,13-26`
- **What's wrong:** `RESEND_WEBHOOK_SECRET` is read into `WEBHOOK_SECRET` but never used. The handler accepts any POST `{type, data}` and inserts it directly into `email_events`. No Svix/HMAC check.
- **Why it's a bug:** `email_events` feeds `send-broadcast` batch dedup and the admin engagement metrics. An unauthenticated caller can forge `sent`/`delivered`/`opened` rows — poisoning metrics and, worse, the batch-segment exclusion set (a forged `sent` for a subject+email silently suppresses a real send). The unused declared secret shows verification was intended.
- **Suggested fix:** Verify the Resend (Svix) signature over the raw body using `RESEND_WEBHOOK_SECRET`; reject with 401 on mismatch.
- **Severity:** High · **Confidence:** High

### H3. `send-broadcast` records cohort sends with `.insert` (not upsert) and only after a whole 100-batch
- **File:** `supabase/functions/send-broadcast/index.ts:267-279`
- **What's wrong:** After a successful Resend batch, cohort sends are written with `.insert(rows)`. If any single row collides with an existing `(campaign_id, user_id)` (overlapping cohort runs), the entire insert fails and **none** of the 100 are recorded → those users get re-emailed on the next run. `run-campaign` deliberately uses `.upsert(..., { onConflict: "campaign_id,user_id", ignoreDuplicates: true })` (run-campaign/index.ts:159-164) to avoid exactly this; the two send paths are inconsistent.
- **Suggested fix:** Use the same `upsert` with `onConflict: "campaign_id,user_id", ignoreDuplicates: true`.
- **Severity:** High · **Confidence:** High

## Medium

### M1. `send-email` skips opted-in notifications when `email_prefs` lacks the specific key
- **File:** `supabase/functions/send-email/index.ts:86-89`, `lib.ts:22-27`
- **What's wrong:** `const prefs = profile.email_prefs || DEFAULT_PREFS;` then `if (!prefs[category]) skip`. The `|| DEFAULT_PREFS` fallback only fires when `email_prefs` is entirely null. If a user has an `email_prefs` object missing a particular key (e.g. an older row predating a new category like `mentions`), `prefs[category]` is `undefined` → falsy → the email is silently dropped.
- **Why it's a bug:** Valid, opted-in users stop receiving a category of notification email purely because their stored prefs JSON predates that category. This contradicts the default-on semantics used in `run-campaign`/`send-broadcast` (`prefs.updates !== false`).
- **Suggested fix:** Merge per key: `const prefs = { ...DEFAULT_PREFS, ...(profile.email_prefs || {}) }`, with an explicit default per category.
- **Severity:** Medium · **Confidence:** High

### M2. `report-notify` returns `{ sent: true }` even when Resend fails
- **File:** `supabase/functions/report-notify/index.ts:76-79`
- **What's wrong:** After the Resend POST it parses the body and returns `{ sent: true }` without checking `emailRes.ok`. A 4xx/5xx from Resend is logged but reported as success.
- **Why it's a bug:** Content-moderation alert emails can silently fail while the caller believes they were sent. Every other email function here checks `res.ok`.
- **Suggested fix:** `if (!emailRes.ok) return 500 with the error body`.
- **Severity:** Medium · **Confidence:** High

### M3. "Recent Opens & Clicks" list is not subject to the founder-email exclusion
- **File:** `index.html:13095-13106` (vs the `bySubjectRows` founder filter at ~13035-13045)
- **What's wrong:** Commit 975ec2e/e695a44 filter founder-only subjects ("New WRotate user:", weekly measurement/analysis) out of `bySubjectRows`, but the `recent` opens/clicks list is only filtered by `myEmail` (the logged-in admin's app email). The founder-only mails go to `ADMIN_EMAIL`. If the admin's app-account email differs from `ADMIN_EMAIL`, opens of those internal emails still surface in "Recent Opens & Clicks."
- **Why it's a bug:** Inconsistent with the stated intent of excluding founder-only emails from the traffic surface; a cosmetic/metrics leak, not a data-corruption issue.
- **Suggested fix:** Apply the same subject exclusion (or a `email_to !== ADMIN_EMAIL` filter) to `recent` before slicing.
- **Severity:** Medium · **Confidence:** Med

### M4. `send-broadcast` batch dedup relies on the async (and forgeable) webhook feed
- **File:** `supabase/functions/send-broadcast/index.ts:205-225`
- **What's wrong:** For `_NofM` segments, dedup queries `email_events` for `event_type='sent'` matching the subject over the last 14 days, then excludes those recipients. The code comment itself notes Resend webhook ingestion lag and advises leaving minutes between batches. If batch 2 runs before batch 1's `sent` webhooks land, the same recipients are re-sent. Combined with H2, the exclusion set is also untrusted.
- **Suggested fix:** Dedup against a synchronous self-written ledger (e.g. `email_campaign_sends`, written immediately after each successful batch as `run-campaign` does), not the eventually-consistent webhook feed.
- **Severity:** Medium · **Confidence:** Med (depends on real batch cadence; design is inherently racy)

## Low

### L1. `convSpread` "BPH-scaled" convergence band is a constant (algebra cancels)
- **File:** `index.html:22667-22668`
- **What's wrong:** `const ppsConv = activeBph / 7200; const convSpread = (86400 / activeBph) * ppsConv;` → `(86400/activeBph)*(activeBph/7200) = 86400/7200 = 12` for every BPH. `activeBph` cancels, so the comment "one quantization step (BPH-scaled)" is false; the gate is a fixed 12 s/day band regardless of 18000/21600/28800.
- **Why it's a bug:** Dead/incorrect logic — the intended BPH-dependent step does not exist. Functionally harmless today because this legacy convergence path is superseded by the v2 plateau controller on 2.0+ builds.
- **Suggested fix:** Use `86400 / activeBph` directly if a real quantization step was intended, and fix the comment.
- **Severity:** Low · **Confidence:** High

### L2. Rate-limit increments are non-atomic read-modify-write (watch-value & identify-watch)
- **Files:** `supabase/functions/watch-value/index.ts:98-113` + `lib.ts:34-39`; `supabase/functions/identify-watch/index.ts:73-116`
- **What's wrong:** Both read the current `rate_limits` row then `.update({ request_count: rl.request_count + 1 })`. Concurrent requests in the same window read the same count and both write `+1` (lost update), so the daily/hourly cap can be exceeded under burst. identify-watch additionally "fails open" on the `.single()` error path, bypassing the limiter on a concurrent first-request unique violation.
- **Suggested fix:** Atomic increment via a SECURITY DEFINER RPC (`request_count = request_count + 1`) or upsert-with-expression.
- **Severity:** Low · **Confidence:** Med

### L3. `rollout-check.py` median takes upper-middle element (slight bias)
- **File:** `scripts/rollout-check.py:164`
- **What's wrong:** `med_spread = spreads[len(spreads) // 2]` returns the upper-middle for even-length lists instead of averaging the two central values. Minor upward bias in the reported repeatability metric (JS `_q2Median` and Python `statistics.median` elsewhere are correct).
- **Suggested fix:** Use `statistics.median(spreads)`.
- **Severity:** Low · **Confidence:** High

### L4. `nightly-analysis.py` inconsistent sign formatting in rate range
- **File:** `scripts/nightly-analysis.py:352,415`
- **What's wrong:** `f"{min(rates):.1f} to {max(rates):+.1f} s/day"` — the lower bound omits the forced sign while the upper bound forces it (e.g. "2.0 to +5.0"). Email-report cosmetics only.
- **Suggested fix:** Use `:+.1f` for both.
- **Severity:** Low · **Confidence:** High

### L5. Web-audio autocorrelation reads a ring buffer as linear after wrap (fallback path only)
- **File:** `index.html:22307-22324`
- **What's wrong:** `envelope` is a ring buffer (`envelope[envW % envCap]`), but the autocorrelation indexes `envelope[i]` for `i in 0..envN` as if time-ordered; after `envW > envCap`, index 0 is no longer the oldest sample. Effect is small (only the single write-head discontinuity) and confined to the non-native web fallback the UI labels "accuracy may be limited."
- **Suggested fix:** Unwrap into a linear array starting at `envW % envCap` before computing mean/variance/autocorr.
- **Severity:** Low · **Confidence:** Med

- **`run-campaign` signup window** — correct non-overlapping 24h slice with `ignoreDuplicates` upsert tracking; comment is stale but logic is fine.

- **`loadAndRenderProfile` collection-visibility gating** (lines 6506-6520) recomputes `vis` from raw `collection_visibility` rather than the normalized `visibility`, but handles legacy `'friends_only'` explicitly, so gating is correct.
